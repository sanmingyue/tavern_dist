# 澜景市世界书侧同步日志与脚本交接回复

本文档是世界书侧对澜景市需求交接文档与脚本侧反馈的响应。

定位：世界书由用户侧负责整理与审定；脚本、前端、存档、路由、解析、数据注入由同事侧负责实现。本文用于让脚本同事或同事的 Agent 明确知道：世界书侧已经怎样承接需求、哪些世界书规则已经定稿、哪些脚本接口仍需配合。

这不是最终导入版世界书，也不是让脚本侧重写世界书的说明。

## 一、双方职责边界

### 世界书侧职责

世界书侧负责：

- 制定澜景市叙事规则。
- 规定扮演模型如何读取权威局势摘要。
- 规定输出标签格式。
- 约束模型不能自行裁决位置、金钱、物品、关系、约定、地标等结果。
- 整理城市、地点、季节、节日、天气、角色、人设、日程、状态、手机行为等世界书条目。
- 根据具体人设和日程继续补充角色世界书。

### 脚本侧职责

脚本侧负责：

- 维护存档结构。
- 维护地图、地点 ID、移动、时间、天气、黄历、日历、约定、资产、角色关系、角色在场等数据。
- 每轮生成前注入世界书扫描词。
- 每轮生成前注入 `【澜景市权威局势摘要】`。
- 解析扮演模型输出的标签。
- 将合法标签写回存档。
- 根据时间、地点、日程、关系、天气等计算当前状态。

双方关系：脚本负责裁决与注入，世界书负责让扮演模型按注入信息叙事。世界书不替代脚本裁决，脚本也不替代世界书进行角色叙事。

## 二、同事反馈与世界书侧理解

同事已交付：

- 小手机相关文件夹。
- 澜景市脚本文件夹。
- 前端导入链接：

```js
import 'https://testingcf.jsdelivr.net/gh/sanmingyue/tavern_dist@lanjing-v0.0.1/dist/澜景市/index.js'
```

同事反馈的关键问题是：

> 地图、日常表、人设没有世界书做不了。

世界书侧对此的理解：

1. 脚本已经有一部分规则裁判能力，但扮演模型不知道澜景市该如何叙事，也不知道怎样使用地图、日程、人设状态。
2. 地图需要世界书提供区域/地点氛围、到达描写规则、地标变化规则。
3. 日常表需要世界书提供“角色不会原地等待”“概率行程只是倾向”“缺省状态如何推断”的规则。
4. 人设需要世界书提供外显/内藏状态、关系记录、手机行为、生活感、说话方式、日程入口等统一模板。
5. 如果世界书不写清楚，扮演模型会容易乱裁决：擅自让角色出现、擅自确认到达、擅自结算关系、擅自知道隐私、擅自生成长期设定。

因此本轮世界书侧先补的是规则框架和模板，而不是直接填具体角色人设。

## 四、世界书侧本轮已完成的审定

以下是用户侧已经做出的世界书审定，不应被后续随意改回。

### 1. 世界书正文不能写成开发说明

世界书正文是给扮演模型看的，不是给开发者看的。

已确认：

- 正式世界书正文里不写“脚本会……”
- 不写“前端会……”
- 不写“AI应该……”
- 不写“系统逻辑是……”

正式世界书应使用类似表达：

- “叙事必须以【澜景市权威局势摘要】为准。”
- “不要直接宣布未被确认的结果。”
- “角色只能知道有来源的信息。”
- “天气只影响倾向，不直接决定结果。”

脚本机制可以写在交接文档中，但不能写进世界书正文。

### 2. `【澜景市权威局势摘要】` 是世界书核心依据

已确认：

- 世界书正文统一使用 `【澜景市权威局势摘要】` 作为当前状态权威来源。
- 如果摘要与过往聊天、推测、印象冲突，以摘要为准。
- 模型只能描写行动、过程、环境反馈和角色反应，不直接裁决存档结果。

### 3. 输出标签按实际 parser 调整

需求文档中给过概念格式，但现有 `tagParser.ts` 实际支持的是 XML-like 标签。

世界书侧已按实际 parser 整理：

- `<时间戳>YYYY-MM-DD HH:mm</时间戳>`
- `<地点变更><locationId>地点ID</locationId></地点变更>`
- `<关系事件 charId="角色ID" delta="数值"><event>...</event></关系事件>`
- `<回忆记录 charId="角色ID">...</回忆记录>`
- `<约定>...</约定>`
- `<地标变更 locationId="地点ID" type="新建">...</地标变更>`

小手机标签保留兼容，但由小手机系统处理，澜景市主 parser 不误解析。

### 4. 玩家状态边界已审定

已确认：

- 年龄、生日属于内藏。
- 八字、时运属于内藏，但可被黄历/玄学生活趣味条目合理参考。
- 私人财务属于内藏。
- 旁白也尽量只写外显，不主动暴露内藏。

### 5. 生活感方向已审定

用户明确修正过“生活感”的定义：

生活感不是“什么样的人就会做什么样的事”，而是身份标签下也有具体日常与反差。

已确认写法方向：

- 表面精英的人也会闲聊饭店、价格和周末。
- 充满勇气的人也会为如何告白为难。
- 温柔的人也会有不想回消息的时候。
- 冷淡的人也可能记得别人随口说过的口味。

世界书中已去掉过度叙事口味和八股描述，改为具体行为约束。

### 6. 角色状态与日程已审定

已确认：

- 如果人设没有写当前状态，模型可以根据人设、时间、地点、天气、关系、近期剧情做轻量推断。
- 轻量推断只用于当前场景，不自动变成永久设定。
- 不允许凭空新增亲属、恋人、病史、创伤、债务、资产、职业、住址、长期秘密或不可逆关系变化。
- 角色日程格式采用：固定行程 + 概率行程 + 特殊行程 + 天气影响 + 状态关联。
- 概率只表示倾向，不由模型自行掷骰决定结果。

### 7. 事件层处理已审定

已确认：

- 黄历只能作为生活趣味和角色参考，不能作为必然命运。
- 天气、季节、节日只影响环境、倾向、话题、阻力和氛围，不能直接裁决剧情结果。
- `WB-303 关系里程碑触发器` 已放弃，不写。

放弃原因：

- 关系推进已由角色规则和标签规范覆盖。
- 额外写关系里程碑容易造成阈值告白、阈值恋爱、阈值决裂。
- 后续关系变化应由具体互动、关系事件、回忆记录和角色行为自然推动。

但当前摘要内容偏少，部分世界书规则还无法充分发挥，需要脚本侧补充字段，见第七节。

## 七、需要脚本侧配合或补传的事项

以下不是世界书侧要求脚本重写，而是根据需求交接文档与当前世界书实现整理出的接口对齐清单。

### 1. `地点到达` 不应每轮常驻触发

当前问题：

- `worldbookRouter.ts` 每轮扫描词都包含 `地点到达`。
- 这会让到达描写条目过度触发。

世界书侧已在 `WB-101` 做保护：没有真实移动时不要强行写到达仪式。

脚本侧建议：

- 只在真实 location change 后注入 `地点到达`。
- 或改成更明确的扫描词，如 `玩法:地点到达`。
- 或注入 `地点到达:是/否`，让世界书更好区分。

### 2. 节日临近接口尚未实现

需求文档要求：

- 节日前 3 天注入 `节日临近:{节日名}`。
- 节日当天注入 `节日:{节日名}`。

当前脚本：

- 只注入 `节日:{festival}`。
- `getNearestFestival` 返回最近节日，但不区分是否临近、是否当天。

世界书侧当前响应：

- `WB-301` 先按当前脚本节日池写：元旦、春游季、中秋、冬日市集。
- 未写春节、端午、七夕、国庆等未接入节日。

脚本侧建议：

- 如要完整实现需求，补 `节日临近:{节日名}`。
- 如扩展节日池，世界书侧再补对应节日条目。

### 3. 黄历已生成但未注入摘要

当前脚本：

- `calendar.ts` 已有 `generateHuangli`。
- 存档中有 `save.calendar.huangli`。

当前问题：

- `worldbookRouter.ts` 的权威摘要未注入黄历内容。

世界书侧已写：

- `WB-008 黄历系统`，定义黄历只是生活趣味，不是命运裁决。

脚本侧建议：

- 在权威摘要中补充今日宜、今日忌、运势标签。
- 例如：`今日黄历：宜..., 忌..., 运势...`。

### 4. 地标变化已支持标签，但摘要未展示当前地点变化

当前脚本：

- schema 中有 `world.landmarks`。
- parser 支持 `<地标变更>`。

当前问题：

- 权威摘要未注入当前位置已有地标变化。

世界书侧已写：

- `WB-102 地标永久变化规则`。

脚本侧建议：

- 若当前地点存在 `save.world.landmarks[locationId]`，在摘要中注入该地点变化描述。

### 5. 在场角色信息过少

当前脚本：

- 在场角色摘要主要是角色名、关系标签、interactionSummary。

世界书侧需要的理想信息：

- 角色当前外显状态。
- 角色当前动作。
- 是否忙碌。
- 手机是否可联系。
- 当前地点出现原因。
- 当前日程来源或约定覆盖。

脚本侧建议：

- 权威摘要可轻量补充在场角色状态。
- 不需要长篇人设，只需给当前可见状态。

### 6. `charSchedules.ts` 仍需实际数据

同事反馈“日常表没有世界书做不了”是成立的；世界书侧已经补了日程规则模板。

但脚本侧如果要真正计算角色在场，需要日程数据。

当前问题：

- `data/charSchedules.ts` 为空。

世界书侧已写：

- `WB-204 Char日程表格式规范`。

脚本侧/后续协作建议：

- 用户提供具体角色日程后，世界书侧按 `WB-204` 整理。
- 脚本侧再将可计算字段映射进 `charSchedules.ts` 或对应存档结构。

### 7. 地点名称与 locationId 需要对齐

世界书中可写地点名称。

但标签中：

```text
<地点变更>
<locationId>地点ID</locationId>
</地点变更>
```

必须使用脚本能识别的 `locationId`。

脚本侧建议：

- 提供常用地点 ID 对照表。
- 将角色日程中的地点名称映射到 `locationId`。
- 避免扮演模型输出不存在的地点 ID。

## 八、后续协作流程

用户已明确要求世界书不能由 Agent 一次性直接生成。

后续继续写世界书时必须按以下流程：

1. 先列出要写的条目。
2. 说明该条目响应需求文档中的哪一项。
3. 说明该条目依赖脚本侧哪个扫描词或摘要字段。
4. 说明严格格式部分。
5. 说明需要用户补充或决定的部分。
6. 先在对话中输出草稿。
7. 用户确认后再录入世界书协作稿。

之前发生过未经审查直接写入的情况，已被用户纠正。后续必须避免。
