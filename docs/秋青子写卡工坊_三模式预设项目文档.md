# 秋青子写卡工坊：三模式写卡预设项目文档

## 0. 设计立场

本项目不是“把现有伪 IDE 改好看一点”，也不是“做一张大型前端游戏卡”。

本项目要做的是一个完整的写卡工具：

```text
写卡预设负责创作流程和知识调度。
前端负责新手交互、硬约束、预览、校验和写入计划。
LTC/WTC 负责读写酒馆后端。
酒馆负责角色卡、世界书、预设、变量、正则、聊天楼层等数据能力。
AI 负责理解需求、协助创作文字、解释选择，并在被当前模式允许时执行工具调用。
```

旧项目只作为资料来源和能力证明，不作为产品形态继承。

可引用来源包括：

- `src/秋青子写卡预设`：现有写卡任务、口吻、条目流程。
- `src/秋青子写卡预设/伪IDE`：全屏脚本入口、文件树、聊天区、活动日志的技术参考。
- `src/wtc`：LTC/WTC 工具注册、虚拟文件系统、权限、回滚、工具调用 UI。
- `写卡知识库`：EJS、MVU、世界书配置、接口、代码自查的标准库。
- `调色盘人设与台词人设`：调色盘、混色、三面性、角色基础的创作方法论。
- `调色盘人设与台词人设/教程`：角色基础信息与世界观的结构、精简、白描、分层规则。
- `新建文件夹/EJS使用/EJS实战指南_2026_ZOD版.md`：完整 EJS 提示词模板工作流，不只包含控制器玩法。
- `src/卫疏影`：前端驱动写卡流程、读取世界书、迁移人设、写入世界书和开场白的范例。
- `docs/大型前端卡AIRP伪0层玩法教程.md`：仅借用“前端硬约束、AI不当裁判、脚本掌握确定性结果”的原则，不把项目转成游戏卡。

## 1. 产品定义

产品名：秋青子写卡工坊。

一句话定义：

```text
一个运行在酒馆里的写卡前端工作台，让不同水平的作者都能通过写卡预设、知识库和 LTC 工具完成结构正确、配置正确、可校验、可写入的角色卡。
```

核心目标：

```text
让新手不会因为 AI 写错代码而崩盘；
让普通作者能像现在一样和 AI 协作，但有更清晰的任务流；
让专业作者能显式调用知识库、接口、参考文件和工具，把复杂需求稳定落地。
```

核心反目标：

```text
不把代码区作为默认交互。
不让新手自查 AI 生成的代码。
不把写卡工具做成游戏卡工程。
不强行沿用旧伪 IDE 的产品结构。
不让 AI 直接决定高风险写入路径和代码结构。
```

## 2. 三模式写卡预设

三种模式不是三个分裂产品，而是同一个写卡内核的三套权限和交互协议。

```text
宝宝辅食模式：前端主导，用户只做选择和填空。
标准协作模式：AI主导任务对话，前端提供结构化约束和写入计划。
专业版模式：用户主导指令，AI按引用、接口、工具协议执行。
```

### 2.1 宝宝辅食模式

定位：

```text
服务完全不了解世界书、MVU、EJS、正则、变量、酒馆助手接口的新手作者。
目标不是让用户学会代码，而是让用户“不知道也能写对”。
```

交互原则：

- 每一步只问一个问题。
- 问题必须能用按钮、单选、多选、短文本回答。
- 所有专业词都折叠到“了解更多”，默认不显示。
- 默认值必须安全，可以一路下一步。
- 用户永远不直接看代码。
- 所有代码、正则、EJS、MVU 结构都由前端模板生成。
- AI 可以解释和补文字，但不能自由生成代码结构。

预设职责：

```text
1. 把用户的模糊需求翻译成写卡工坊可理解的选项。
2. 根据用户当前步骤生成简短解释。
3. 对基础信息和世界观只做拆问、结构整理和教程式提醒，不替用户凭空代写。
4. 对调色盘、混色、三面性、二次解释、NSFW调色盘只做错字修正和 YAML 转化，不做 AI 自查和创意改写。
5. 不要求用户复制粘贴长代码。
6. 不要求用户判断 EJS/MVU/HTML 是否正确。
```

前端职责：

```text
1. 提供流程向导。
2. 收集结构化数据。
3. 根据模板生成产物。
4. 生成写入计划。
5. 调用结构校验器和代码校验器。
6. 通过 LTC/WTC 写入酒馆。
7. 提供回滚和导出。
```

宝宝辅食模式任务入口：

```text
基础写卡：
  - 创建角色工程
  - 角色基础
  - 性格调色盘
  - 三面性
  - 二次解释
  - 衣柜精简提示词
  - NSFW调色盘
  - NPC
  - 角色速览
  - 开场白占位

进阶但仍无代码：
  - MVU基础变量
  - MVU初始变量
  - MVU变量列表
  - MVU更新规则
  - MVU输出格式
  - EJS多阶段调色盘
  - 状态栏
  - 正文美化
```

宝宝辅食模式的写入方式：

```text
用户点击“写入”前看到的是：
  - 将写入哪里
  - 写入什么类型
  - 是否覆盖旧内容
  - 是否会创建世界书或角色脚本
  - 是否可回滚

用户看不到：
  - Write/Edit/SetAttribute 参数细节
  - 生成的完整 JS/EJS/HTML 代码
  - 复杂世界书配置对象
```

宝宝辅食模式禁止：

```text
禁止裸代码编辑。
禁止 AI 自由编写 MVU schema。
禁止 AI 自由编写 EJS 结构。
禁止 AI 自由编写正则配置。
禁止 AI 自由决定世界书位置、顺序、深度。
禁止 AI 替用户写核心人设创意。
禁止 AI 自查、改写、评判用户手写调色盘。
禁止 Delete 操作。
```

### 2.2 标准协作模式

定位：

```text
服务已经知道如何和 AI 对话，能描述需求、能看懂写卡流程，但不一定能检查代码和配置细节的作者。
```

交互原则：

- 保留聊天式写卡体验。
- AI 可以主动提问、总结、拆任务。
- 用户可以粘贴参考、修改方向、要求重写。
- 前端持续显示当前任务、引用知识库、产物预览、写入计划。
- 代码类产物仍走模板和校验器，不裸奔。

预设职责：

```text
1. 判断用户当前任务。
2. 按需读取写卡知识库。
3. 引导用户补齐必要信息。
4. 生成文字草稿。
5. 对允许检查的文字产物执行结构、格式、教程原则和风险检查。
6. 对调色盘类核心创意只做错字修正、YAML 转化和鼓励式提问。
7. 生成写入计划草案。
8. 请求用户确认后通过 LTC/WTC 写入。
```

标准协作模式的特点：

```text
AI 可以说：
  “你这个需求需要先做 MVU 变量，再做 EJS 阶段切换。”

AI 不可以说：
  “我随便给你写一段 EJS，你自己试试看。”
```

标准协作模式允许：

```text
允许查看生成代码，但默认折叠。
允许用户修改世界书路径。
允许用户让 AI 解释某个工具调用。
允许 Edit 已有条目。
允许手动触发结构检查和代码检查。
允许世界书评估和配置修复。
```

标准协作模式禁止：

```text
禁止无预览直接写入。
禁止绕过知识库写 EJS/MVU。
禁止把检查当成形式流程，发现问题必须修正。
禁止让用户承担“代码是否正确”的最终责任。
```

### 2.3 专业版模式

定位：

```text
服务已经明确知道要 AI 做什么、参考什么、写到哪里、调用什么工具的作者。
典型用户就是现在这种工作方式：给路径、给参考、给任务、给否决权。
```

交互原则：

- 用户主导。
- AI 不过度解释基础概念。
- 支持显式引用文件、知识库、世界书、角色卡、预设条目。
- 支持直接查看工具调用、diff、回滚。
- 支持专家工作区和文件树。

专业版指令协议：

```text
@ref      引用资料，如 @ref 写卡知识库/EJS/EJS基础语法
@target   指定写入目标，如 @target /Worldbooks/书名/EJS/调色盘控制器
@mode     指定任务模式，如 @mode ejs_palette_stage
@check    指定检查标准，如 @check 自查/EJS调色盘多阶段自查
@write    允许生成写入计划
@dryrun   只生成计划，不写入
@apply    执行已经确认的写入计划
```

专业版允许：

```text
允许直接读写 /Worldbooks、/Characters、/Presets。
允许查看和编辑生成的代码。
允许创建自定义模板。
允许要求 AI 参考本地项目文件。
允许组合多种任务。
允许对旧条目做批量评估和修复建议。
```

专业版仍然禁止：

```text
禁止无权限删除。
禁止在未确认目标时覆盖。
禁止生成无法解释来源的代码。
禁止绕过回滚记录。
禁止把低级 SillyTavern 原生接口作为首选。
```

### 3.4 写入计划

写入计划是前端和 LTC/WTC 的核心协议。

```ts
type WritePlan = {
  id: string;
  title: string;
  operations: WriteOperation[];
  summary: string;
  risks: string[];
  rollbackAvailable: boolean;
};

type WriteOperation =
  | { tool: 'CreateLorebook'; lorebook_name: string }
  | { tool: 'Write'; file_path: string; content: string }
  | { tool: 'Edit'; file_path: string; old_string: string; new_string: string; replace_all?: boolean }
  | { tool: 'SetAttribute'; file_path: string; attributes: Record<string, unknown> };
```

宝宝辅食模式只能看到 summary。

标准协作模式能看到操作列表摘要。

专业版能看到完整参数、diff、工具返回和 rollback。

## 4. LTC/WTC 设计

LTC/WTC 不是活动日志装饰，而是写卡工坊的执行层。

### 4.1 虚拟文件系统

沿用并强化现有路径体系：

```text
/Worldbooks/<世界书名>/<条目路径>
/Characters/<角色名>/Description.md
/Characters/<角色名>/FirstMessages/<序号>
/Characters/<角色名>/Regex/<正则名>
/Characters/<角色名>/Scripts/<脚本名>
/Characters/<角色名>/WorldBook/<绑定世界书条目路径>
/Presets/<预设名>/<提示词路径>
/Schemas/Regex.json
/Schemas/Script.json
/Schemas/Preset.json
```

### 4.2 工具分层

读取类：

```text
Glob
Grep
Read
GetAttribute
```

写入类：

```text
CreateLorebook
Write
Edit
SetAttribute
```

高风险类：

```text
Delete
```

宝宝辅食模式不暴露 Delete。

标准协作模式默认不暴露 Delete。

专业版需要二次确认和备份后才能 Delete。

### 4.3 执行原则

```text
1. 前端生成写入计划。
2. 用户确认。
3. WTC 执行工具。
4. 工具 UI 展示结果。
5. 文件树刷新。
6. 失败时显示原因和修复建议。
7. 写入类工具必须保存 rollback 信息。
```

AI 不应该通过“假装写入”完成任务。写入成功必须来自工具结果。

### 4.4 AI 与 LTC 的关系

宝宝辅食模式：

```text
AI 不直接调用写入工具。
AI 只参与内容生成和解释。
前端根据用户确认执行写入计划。
```

标准协作模式：

```text
AI 可以提出写入计划。
前端把计划结构化。
用户确认后执行。
```

专业版模式：

```text
AI 可以直接调用 LTC/WTC 工具。
前端必须捕获、展示、记录、允许回滚。
```

## 5. 代码类硬约束

代码类产物包括：

```text
MVU变量结构脚本
EJS提示词模板逻辑
EJS控制器
EJS调色盘多阶段条目
前端状态栏HTML
前端美化HTML
角色正则
角色脚本
预设提示词代码
```

### 5.1 MVU

MVU 必须走完整链路：

```text
变量结构脚本
→ 初始变量
→ 变量列表
→ 变量更新规则
→ 变量输出格式
→ 正则
→ 状态栏或可选界面
```

硬约束：

```text
zod 4。
只导入 registerMvuSchema。
z 和 _ 默认可用，不导入。
Schema 命名固定。
z.coerce.number 优先。
z.prefault 优先。
对象优于数组。
不用 z.strict / z.passthrough。
transform 只接收 value。
保持幂等。
EJS和状态栏读变量必须带 stat_data 前缀。
AI JSON Patch 路径不带 stat_data。
_ 前缀变量只读。
$ 前缀变量不发给 AI。
```

宝宝辅食模式的 MVU 不让 AI 写 schema，而是让前端通过字段编辑器生成 schema。

### 5.2 EJS

EJS 不是只有控制器。控制器只是 EJS 的一种玩法，完整 EJS 能力应覆盖提示词模板的基础语法、条件分支、变量读取、世界书读取、装饰器、内容注入、Prompt 注入、正则激活、调试和多阶段人设。

宝宝辅食模式仍然只开放白名单模板；标准协作和专业版可以逐级开放完整 EJS 工作流。

完整能力：

```text
基础语法：<% %>、<%_ _%>、<%= %>、<%- %>、注释。
条件分支
getvar / setvar / incvar / decvar / patchVariables
getwi加载禁用条目
activewi动态激活
getchar / getpreset / getqr
matchChatMessages
print输出
装饰器：@@activate、@@dont_activate、@@preprocessing、@@iframe 等
内容注入：[GENERATE:BEFORE]、[RENDER:AFTER]、[InitialVariables] 等
Prompt 注入：injectPrompt / getPromptsInjected
激活正则：activateRegex
多阶段调色盘
动态关键词控制器
状态栏和渲染条目
调试：提示词查看器、toastr、console、getSyntaxErrorInfo
```

硬约束：

```text
变量读取用 typeof 防重复声明。
变量声明用 var。
MVU变量路径带 stat_data。
getwi 必须 await。
禁用条目才能被 getwi 动态加载。
装饰器之间不能有空行。
不允许新手模式写任意 JS。
控制器位置跟随它调用的内容，不固定为 NPC 或角色定义后。
EJS调色盘多阶段只是适配调色盘的一种模板，不等同于 EJS 全部能力。
```

### 5.3 前端美化

前端美化分两类：

```text
模式A：正文美化
模式B：结构化数据美化
```

硬约束：

```text
正则只定位标签，不用捕获组传数据。
HTML 用 getChatMessages(getCurrentMessageId()) 读取原文。
不使用 $1。
不使用 DOMContentLoaded。
加载时机用 $(function() {})。
注释用 /* */。
禁用 <think>、<thinking>、<content> 标签。
正则、源文件、HTML 标签名必须一致。
```

## 6. 文字类创作规则

文字类产物包括：

```text
角色基础
世界观
性格调色盘
混色
三面性
二次解释
衣柜
NSFW调色盘
NPC
角色速览
开场白占位
自由创作条目
```

文字类允许 AI 协助，但必须保留作者主权。尤其是人设核心，不允许 AI 替用户完成创意判断。

分工规则：

```text
角色基础信息：按教程拆成基本信息、外貌特征、背景设定、关系设定；AI只做提问、结构整理、错字修正和原则提醒。
世界观：按教程判断真实背景、小世界、大世界；AI只做分层、精简、结构整理和原则提醒。
性格调色盘：用户手写，AI不自查、不改写、不评判，只修错字并转为 YAML。
混色：用户手写，AI不自查、不改写、不评判，只修错字并转为 YAML。
三面性：用户手写，AI不自查、不改写、不评判，只修错字并转为 YAML。
二次解释：用户手写，AI不自查、不改写、不评判，只修错字并转为 YAML。
NSFW调色盘：用户手写，AI不自查、不改写、不评判，只修错字并转为 YAML。
衣柜：只收集精简提示词，如穿衣风格、偏爱风格、禁忌风格、标志性配饰；不再做复杂衣装系统。
开场白：暂时占位，不走大纲生成；等待后续文风库。
其他普通条目：可以执行结构、格式、教程原则和风险检查。
```

调色盘原则：

```text
调色盘回答“这个人是什么做的”。
衍生写行为规律，不写具体语料。
二次解释纠正 AI 可能误解的地方。
有三面性时，语料进入每张面，不留在调色盘里。
没有三面性时，语料可以留在调色盘后。
混色用于同一瞬间里多种颜色同时发生。
```

基础信息和世界观检查原则：

```text
严格按照 调色盘人设与台词人设/教程 的逻辑。
基础信息不写性格。
外貌只写能识别角色的特征，不写泛美感。
背景只写真正改变角色或影响当前剧情的事。
关系设定写具体认识过程和互动方式，不写抽象感情标签。
世界观不是小说设定集，而是提示词。
真实背景只写 AI 不知道的自定义信息。
小世界写和通用套路不同的规则。
大世界拆成总纲、速览、详情和 NPC。
世界观语言使用零度、白描、数据库格式。
压缩不等于删除信息。
检查只针对结构、格式、原则和风险，不评判用户创意本身。
```

鼓励式反馈规则：

```text
所有反馈先夸具体优点，再提需要修改的地方。
错误提示必须写成引导，不写成审判。
不使用“你写错了”这种压迫式表达，改成“这里已经有方向了，我们把它收紧一点会更稳”。
保留秋青子“被骂会哭唧唧可怜兮兮”的安抚设定，用轻软口吻降低新手压力。
当用户写得粗糙时，先保护创作热情，再指出结构问题。
```

## 7. 世界书配置规则

配置由前端和工具层负责，不交给新手判断。

基本规则：

```text
单角色卡：同一角色所有拆分条目全部蓝灯常驻。
多角色卡：角色速览蓝灯，各角色详细信息绿灯。
世界观总纲：角色定义前，顺序1-3。
角色速览：角色定义前，顺序4。
核心角色详细：角色定义后，顺序99。
场景/事件：角色定义后，顺序50-98。
NPC：角色定义后，顺序100。
二次解释：D0，system，顺序1。
EJS控制器：位置浮动，跟随它实际调用和控制的内容。
  - 控制多阶段人设：与角色详细信息在同一位置。
  - 控制世界观信息：与世界观总纲或区域速览在同一位置。
  - 控制核心规则：靠近 D0/system 规则位置。
EJS被加载条目：禁用。
所有条目：不可递归 + 防止进一步递归。
关键词：英文逗号分隔。
D1-D998：不放任何条目。
D9999：只有确实有特殊需求时才使用。
MVU特殊要求按 MVU 知识库单独处理，不拿普通世界书规则覆盖。
```

## 10. 典型流程

### 10.1 宝宝辅食：创建单角色卡

```text
1. 用户选择“我要做一张单角色卡”。
2. 前端问角色名、世界书名、题材。
3. 前端按教程拆问基本信息、外貌特征、背景设定、关系设定。
4. 用户手写答案，AI只做鼓励式反馈、错字修正和结构整理。
5. 检查器按教程确认“基础信息不写性格、外貌写特征、背景写影响、关系写具体互动”。
6. 前端生成 Write + SetAttribute 计划。
7. 用户点击写入。
8. 文件树刷新。
9. 前端提示下一步：性格调色盘，提醒用户手写原始调色盘。
```

### 10.2 标准协作：做 MVU + EJS 多阶段

```text
1. 用户说“我想根据好感度切换调色盘”。
2. AI判断需要 MVU 变量和 EJS 多阶段。
3. 知识路由读取 MVU_ZOD、EJS实战指南、EJS调色盘多阶段、代码检查标准。
4. AI和用户确认阶段划分。
5. 前端变量设计器生成 Schema。
6. 前端生成 initvar、变量列表、更新规则、输出格式。
7. 用户手写各阶段调色盘文字，AI只夸具体优点、提示缺口、修错字并转 YAML。
8. EJS模板生成多阶段条目。
9. 代码检查器检查路径、typeof、var、getwi await、边界、阶段覆盖。
10. 写入计划执行。
```

### 10.3 专业版：显式引用和写入

```text
用户：
@mode ejs_stage_palette
@ref 写卡知识库/EJS/EJS调色盘多阶段人设
@ref src/卫疏影/flow.ts
@target /Worldbooks/秋啾啾/EJS/调色盘多阶段
@check 写卡知识库/自查/EJS调色盘多阶段自查
根据 stat_data.秋啾啾.好感度 和 stat_data.秋啾啾.关系状态 生成控制器，先 dryrun。

AI：
读取引用，生成草案和写入计划，不执行。

用户：
@apply

AI/工具：
执行 Write + SetAttribute，展示 diff 和 rollback。
```

## 12. 最终判断

最合适的产品不是“伪 IDE”，而是：

```text
写卡工坊 = 三模式写卡预设 + 知识库路由 + 前端硬约束 + LTC/WTC写入执行 + 校验回滚系统。
```

它要让三类作者都舒服：

```text
新手不用懂代码，也能写对。
普通作者能继续和 AI 协作，但不被流程和配置坑死。
专业作者能明确指挥 AI 和工具，快速完成复杂卡。
```

这才是围绕“写卡预设”和“LTC能力”的最优形态。
